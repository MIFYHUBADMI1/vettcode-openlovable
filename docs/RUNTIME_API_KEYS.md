# Atai Runtime — API Key Lifecycle (Developer Guide)

> Scope: the credential system for applications generated by Atai. This is a
> **customer credential for the Atai Runtime API** — it is not an Atai internal
> authentication mechanism and never exposes provider credentials.

## Key format

```text
atai_<environment>_<secret>
atai_production_b3xK9mQ2...
atai_development_b3xK9mQ2...
```

- Secret: 32 cryptographically random bytes (`node:crypto.randomBytes`),
  base64url-encoded — URL/header safe, ~256 bits of entropy.
- The environment segment is visible in the prefix for quick identification.
- Never predictable: no timestamps, user/project IDs, ObjectIds, or UUIDs.

## One-time secret behavior

The plaintext secret is shown **exactly once**, in the response of key
creation or key rotation. It is never retrievable again — there is no
"resend" or "reveal" operation. If lost, rotate the key.

## Hashing & storage

| Stored | Not stored (anywhere) |
|---|---|
| `keyHash` (SHA-256 hex of the full secret) | plaintext key, `key`, `secret`, `apiKey`, `fullToken` |
| `keyPrefix` (env + first 4 secret chars, e.g. `atai_production_a81f…`) | hashes in public responses or logs |

- SHA-256 is appropriate because the secret is high-entropy random (not a
  human password); lookup is an indexed O(1) equality. bcrypt is deliberately
  not used — it is reserved for passwords.
- `keyHash` has a **unique** MongoDB index; the lookup `hash → api_keys` is
  the future runtime authentication primitive.

## Ownership model

```text
api_key → userId (Atai account, billing root)
        → projectId (Atai project / generated app)
        → environment (development | production)
```

No Account/Organization/Team entities exist or are created. Every management
operation takes the `userId` from the **Atai session** (`requireUser`), never
from the client body. Cross-user access is structurally impossible: ownership
predicates are part of every query filter.

### Multi-project / multi-key model

A user may own many projects and hold many keys:

```text
Atai User A
├── Project A   → development key + production key
├── Project B   → development key + production key
└── Project C   → development key + production key (+ rotation history)
```

The only unique constraint is on `keyHash` — there is deliberately **no**
`unique(userId, projectId, environment)` rule, so a project may hold any
number of keys (development, production, rotation overlap, separate
application instances, future service credentials). A key belonging to
Project A can never authorize Project B: the binding is a stored property
of the key, and the future runtime identity (`apiKeyId, userId, projectId,
environment, scopes`) is derived exclusively from the presented key.

### Programmatic provisioning (future integration point)

`provisionApiKeyForProject({ projectId, environment, scopes, name?, expiresAt? })`
creates a key for a project, deriving ownership from the project record
server-side — the hook the future Generated Application Integration phase
will call after a successful build (before injecting credentials into the
generated app). Automatic provisioning is NOT wired into the build pipeline
yet; `scopes` are explicitly required (the service never silently grants
"all capabilities").

## Environments

`development` and `production` are stored on the key. A production key never
behaves as a development key and vice versa — the future runtime
authentication layer will enforce that the key's environment matches the
request context. There is no `runtime_environments` collection.

## Scopes

Keys carry capability scopes from the Phase 2 contract
(`ai.text`, `search.web`, `payments`, …). Scopes are **authorization
metadata only** — a scope listed on a key does not imply the capability is
implemented. An empty array means "all capabilities granted". Future
dotted sub-operations (e.g. `ai.image.generate`) are tolerated by the
validator without invalidating existing keys.

## Lifecycle

| Operation | Behavior |
|---|---|
| **Create** | Validate input → verify project ownership (session user) → generate secret → store hash → return metadata + plaintext once. Rate-limited per user (20/day). |
| **List** | Metadata only (`GET /api/runtime/keys?projectId=…`): id, name, projectId, environment, scopes, status, keyPrefix, createdAt, lastUsedAt, expiresAt, revokedAt, revokedReason, rotatedFromId, rotatedToId. Never `keyHash`, never `secret`. |
| **Get one** | `GET /api/runtime/keys/:keyId` — same metadata, ownership-filtered; another user's key is indistinguishable from a missing one (404). |
| **Revoke** | `DELETE /api/runtime/keys/:keyId` — status → `revoked`, `revokedAt` + sanitized `revokedReason` recorded. The record is **never deleted** (audit/usage history). Revoked keys can never authenticate. |
| **Rotate** | `POST /api/runtime/keys/:keyId/rotate` — atomic transaction: create new key (fresh secret, `rotatedFromId` set) → retire old (`status: revoked`, `rotatedToId` set) → return new plaintext once. No grace period: the old credential is immediately invalid. Concurrent rotations are safe — the loser's conditional update matches nothing and the transaction aborts. |
| **Expire** | Optional `expiresAt` (epoch ms) at creation. Expiration is an authorization state (`now >= expiresAt` ⇒ expired), **not deletion** — records persist. Helper: `effectiveKeyStatus()`. |

## Management API (session-authenticated, dashboard-facing)

```text
GET    /api/runtime/keys?projectId=<id>     list keys for a project
POST   /api/runtime/keys?projectId=<id>     create key → one-time secret
GET    /api/runtime/keys/:keyId             key metadata
DELETE /api/runtime/keys/:keyId             revoke
POST   /api/runtime/keys/:keyId/rotate      rotate → one-time new secret
```

These are **management** routes, distinct from the future public runtime
invocation API (Bearer-key authenticated). They reuse the existing response
envelope (`ok()`/`fail()`), error codes, and rate limiter.

## Security expectations

- Plaintext secrets are never persisted in MongoDB, project/user documents,
  Totalum, logs, analytics, or runtime usage records.
- Logs carry only safe identifiers (`apiKeyId`, `keyPrefix`, `projectId`,
  `userId`, `environment`) through the existing redacting logger.
- Errors are stable and machine-readable; key state and existence are never
  revealed to unauthenticated or unauthorized callers.
- `ATAI_INTERNAL_KEY` is unrelated to this system and is never consulted.
- Provider credentials (OpenRouter, Firecrawl, ElevenLabs, Dodo, …) are never
  involved in the key lifecycle and remain server-side behind the Runtime API.
