# Atai Runtime API + Router + SDK — Phase 1 Architecture Report

> **Status: DISCOVERY ONLY — NOT IMPLEMENTED.** This document is the output of a read-only
> audit of the existing Atai codebase. Nothing in the existing pipeline, billing system,
> or Totalum integration was modified. Implementation must not begin until this
> architecture is explicitly approved.

## Confirmed product context (from product-owner discussion)

The following are **decisions**, not proposals. The architecture below is built on them:

1. **Two planes.** Plane 1 — Atai Build Infrastructure (planning, collaboration plans,
   pipelines, specifications, Totalum generation). Plane 2 — Atai Runtime Power Layer
   (SDK + Runtime API + Router) used **by the generated applications**, not by Atai's own
   pipeline. Atai's internal pipeline keeps using its current infrastructure unchanged.
2. **The problem being solved:** Totalum-generated apps would otherwise prompt founders
   to configure `OPENAI_API_KEY`, `FIRECRAWL_API_KEY`, `STRIPE`, etc. — unacceptable for
   the target customer (non-technical founders). One credential, `ATAI_API_KEY`, replaces
   all of them.
3. **End users are NOT Atai users.** A generated app's end customers are two levels
   below Atai. Their requests flow: End user → Generated app → Atai SDK → Runtime API →
   Router → Provider. All attribution lands on the founder's Atai account.
4. **Model tiers.** Generated apps may let their end users select models (e.g. free
   users → basic models, paid users → premium models). Model access/tiering is enforced
   by the Router, informed by the founder's account entitlements.
5. **Payments default = Dodo**, deliberately: the founder cannot obtain a Stripe account
   in their current geography. Stripe may be added as a second payments adapter later,
   but Dodo is the initial and default provider behind `atai.payments`.
6. **CDN capability (`atai.cdn`)** is also desired as an abstraction over Cloudflare
   (cache/purge/invalidate/rules/status) — infrastructure-level, not application-AI.
   Added to the capability matrix as UNVERIFIED.
7. **Business model:** metered runtime usage billed against the founder's Atai account
   creates a recurring relationship that outlasts one-time app generation.

**Core principle (restated):**
> Atai builds the application. The Atai Runtime API powers the application after it is
> built. The generated application uses the Atai SDK and an Atai API key. The Atai API
> key is bound to the correct Atai account/project, and runtime usage is attributed to
> that account. Provider credentials remain behind Atai.

## A. Current architecture summary

What the audit found about the existing Atai application:

| Aspect | Finding |
|---|---|
| Framework | **Next.js 16.3.3** (App Router), React 19, TypeScript 5.7 strict mode. Note: `proxy.ts` is the Next 16 replacement for `middleware.ts`. |
| Repo shape | **Single Next.js application, not a monorepo.** `pnpm-workspace.yaml` exists but contains no `packages:` field — it only pins `minimumReleaseAgeExclude` for Next packages. Package manager is pnpm (package-lock.json is also present, a hygiene issue worth noting separately). |
| Database | **MongoDB Atlas** via the `mongodb` driver (v7). No ORM/Mongoose. One shared `getDb()` client (`lib/db/mongodb.ts`), typed collection accessors + idempotent index creation in `lib/db/collections.ts`. Collections are informal (no schema enforcement beyond TypeScript types). |
| Auth | Home-grown: opaque session token in an httpOnly cookie (`Atai_session`), SHA-256 hash stored in `sessions` with TTL; bcrypt password hashing; Google + GitHub OAuth; email verification tokens (hashed, TTL'd). Guards: `requireUser()`, `requireAdmin()` throwing typed `AppError`s. Edge `proxy.ts` short-circuits cookie-less `/api/*` requests. |
| Identity model | **Flat single-tenant model: one `users` collection, no accounts/orgs, no teams tables.** `UserDoc.id` is the ownership root (`user_...`). Projects, ledger entries, sessions, referrals all reference `userId` directly. There is no Account entity between user and project. |
| Projects | `MirrorProject` (`projects` collection) — the full build-time lifecycle: idea/URL input → understanding → `ApplicationSpecification` → build (`build_runs`, Totalum VCaaS) → deployment (`deploymentHistory`, `publish_events`). `totalumProjectId` links a project to its generated Totalum application. |
| Build pipeline | Planning orchestrator (`lib/planning/`) with multi-stage AI pipeline (OpenRouter via `@ai-sdk/openai-compatible`), critique/repair/validation stages, heavy/legacy modes. Build-time only — this is what must NOT be touched. |
| Generated apps | Generated by **Totalum VCaaS** (`lib/integrations/totalum/`). Atai holds ONE platform-wide `TOTALUM_API_KEY` server-side. Generated apps get deployment URLs (subdomain or custom domain), and secrets can be written into the Totalum project via `POST /projects/:id/secrets` (exposed in `app/api/projects/[id]/secrets/route.ts` — keys are created with values the user supplies; the UI surfaces `buildSummary.secretKeysNeeded`). |
| Billing | Unified double-entry **credit ledger** (`credit_ledger`, `lib/billing/credit-service.ts`) with idempotency keys, Mongo transactions, subscription/permanent credit buckets consumed oldest-expiry-first. Build authorization flow (reserve → execute → finalize/release). Payments via **Dodo** (`dodopayments` SDK), Standard-Webhooks HMAC verification, webhook event log. Admin-configurable runtime pricing in `app_settings` (`lib/billing/runtime-config.ts`). |
| Usage tracking | `provider_usage` collection (provider, operation, userId, projectId, cost estimate) — currently tracks build-time Firecrawl/Totalum/ImageKit/email usage. |
| Rate limiting | Mongo fixed-window limiter (`lib/auth/rate-limit.ts`, atomic `findOneAndUpdate`), used per-action. |
| Error handling | Central `AppError` code registry (`lib/errors.ts`) + `ok()/fail()/handleRouteError()` envelope (`lib/api/respond.ts`). `{ ok: true, data }` / `{ ok: false, error: { code, message } }`. |
| Logging | Structured JSON logger with secret redaction by key-name pattern (`lib/logging/logger.ts`). |
| Existing internal API | `app/api/internal/*` — server-to-server endpoints authenticated by a shared static secret `ATAI_INTERNAL_KEY` header. This is the only precedent for non-session API auth, and it is weak (static shared secret, plain comparison, verbose logging of key material — noted as a risk to avoid repeating). |
| Testing | Vitest, node environment, `@/` alias. 46 test files detected. |
| Env config | Per-feature lazy env getters (`lib/env.ts`) that throw typed errors only when a feature is used. |

**Key gaps relevant to the Runtime API:**
- No Account/Organization entity (ownership is flat user → project).
- No environments concept anywhere (Totalum secrets have an `environment` field, but Atai does not).
- No API-key table, no non-session credential mechanism except the static internal key.
- No service that charges credits per-request at runtime (all existing charging is build-time, route-scoped).
- No public, versioned, machine-facing API surface.

This is the **logical** structure: three cleanly separated components sharing one

   All infrastructure it needs (Mongo client, credit ledger, rate limiting, error
   envelope, logging) is already shared in-repo. When load or blast-radius justifies
   it, the same code extracts into `apps/runtime-api` as a pnpm workspace app — no
   rewrite, because the code is already isolated behind its own module boundary.
2. **Atai SDK** becomes `packages/atai-sdk` — a true, separate workspace package from
   day one of SDK work (Phase 7), published independently, containing only the client,
   capability APIs, types, and error mapping. It never contains provider secrets.
3. **Existing Atai application** is not moved, renamed, or restructured at any point.

```text
atai/ (repo, evolved additively)
├── app/api/runtime/v1/…        # NEW — Runtime API routes (public, key-authenticated)
├── lib/runtime/                # NEW — runtime service core (server-only)

```

## C. Runtime service boundary

**Belongs inside the Runtime API:**
- Key authentication and resolution (key → user → project → environment)
- Capability authorization (scopes on the key)
- Entitlement/balance checks and per-request credit consumption
- Capability routing and provider adapter invocation
- Response normalization and error normalization
- Usage measurement + recording (`runtime_usage` events, credit ledger debits)
- Rate limiting and abuse controls for runtime traffic
- Key management endpoints (dashboard-facing, session-authenticated)

**Explicitly does NOT belong:**
- Anything from the build pipeline (planning, specs, collaboration, Totalum builds)
- Totalum project management (agent runs, deployments, versions) — stays build-time
- Existing dashboard billing pages, Dodo checkout, webhooks — unchanged
- The existing `/api/internal/*` endpoints — unchanged (though their auth pattern
  should be treated as legacy and not extended)

## D. Database architecture

### Existing entities reused (no changes required)

| Collection | Reuse |
|---|---|
| `users` | **Ownership root.** `UserDoc.id` is the Atai account for all runtime attribution. No new account table. |
| `projects` | `MirrorProject` — `totalumProjectId` identifies the generated application. Runtime keys reference `projectId` (and derive `userId` from it). |
| `credit_ledger` | Runtime consumption is recorded here via new `LedgerTransactionType` values (`runtime_usage`, `runtime_reservation`, `runtime_refund`) — additive enum change only. |
| `provider_usage` | Pattern precedent; runtime gets its own dedicated collection for richer per-request telemetry. |
| `rate_limits` | Reused via `checkRateLimit` with new action names (`runtime:key`, `runtime:project`). |
| `app_settings` | New `runtime` section for admin-configurable limits/pricing defaults (same layering pattern). |

### New runtime collections

```text
api_keys                    (new)
runtime_environments        (new — lightweight)
runtime_usage               (new)
runtime_requests            (new, optional — see note)
```

**`api_keys`** — the core credential:

```typescript
interface ApiKeyDoc {
  _id: ObjectId
  id: string                       // key_<id> — safe, non-secret reference
  userId: string                   // Atai account (owner) — REQUIRED, indexed
  projectId: string                // Atai project the key serves — REQUIRED, indexed
  environment: "development" | "production"  // see note below
  name?: string                    // display label
  keyHash: string                  // SHA-256 of the full secret — unique index
  keyPrefix: string                // first 8 chars, for dashboard display ("atai_ab12…")
  scopes: CapabilityScope[]        // e.g. ["ai.text", "search.web"] — default: all granted
  status: "active" | "revoked" | "expired"
  createdAt: number
  lastUsedAt?: number              // updated opportunistically (throttled)
  expiresAt?: number               // optional expiry
  revokedAt?: number
  revokedReason?: string
  rotatedFromId?: string           // lineage for rotation
  rotatedToId?: string
}
// Indexes: { keyHash: 1 } unique · { userId, createdAt: -1 } · { projectId, status }
```

Secret format: `atai_<environment>_<32+ urlsafe-random bytes>`, generated with
`crypto.randomBytes`, shown **once** at creation, stored only as a hash (same pattern
as `lib/auth/crypto.ts` `generateToken`/`hashToken`).

**`runtime_environments`** — likely **NOT needed as a collection.** The existing system
has no environment concept; the pragmatic move is a two-value enum on the key
(`development` | `production`) that selects per-environment provider configs in
`lib/runtime/providers/`. Escalate to a real collection only if per-environment
configuration becomes user-editable. *(This is one of the "only if actually necessary"
calls requested — it isn't, initially.)*

**`runtime_usage`** — one event per provider call:

```typescript
interface RuntimeUsageDoc {
  _id: ObjectId
  id: string
  requestId: string
  userId: string; projectId: string; apiKeyId: string; environment: string
  capability: string               // "ai.text", "search.web"
  operation?: string               // e.g. "image.generate"
  provider: string; model?: string
  status: "succeeded" | "failed"
  latencyMs: number
  usage?: Record<string, unknown>  // tokens, creditsUsed etc. — provider-reported
  costMetadata?: Record<string, unknown>  // provider cost inputs (NO secrets)
  creditsCharged: number
  errorCategory?: RuntimeErrorCode
  createdAt: number                // TTL after N days (admin-configurable)
}
```

**`runtime_requests`** — a fuller request log (headers summary, sizes, IP hash). Given
`runtime_usage` already covers attribution, make this **optional/deferred** and enable
only if debugging requires raw request telemetry. Redaction rules from
`lib/logging/logger.ts` apply (never store secrets; request bodies not persisted).

**Attribution chain (final):**

```text
api_key ──▶ user (Atai account, existing) ──▶ credit_ledger charges
   └──────▶ project (existing) ──▶ runtime_usage events
```

No new user/account system; `users` remains the single identity source. No FKs exist in
Mongo — references are by string `id`, consistent with every existing collection.

## E. API key lifecycle

| Operation | Design |
|---|---|
| **Create** | Dashboard (session-auth `requireUser()` + project-ownership check, mirroring `secrets/route.ts`). POST returns the plaintext secret exactly once. Scope set + environment chosen at creation. |
| **List** | GET returns metadata only (`keyPrefix`, scopes, status, lastUsedAt) — never the secret. |
| **Rotate** | POST creates a new key with copied scopes (`rotatedFromId`), marks old key `revoked` with a grace-window field (`deactivateAt`) so both validate during overlap, then old key auto-expires. |
| **Revoke** | Immediate: set `status: "revoked"`, `revokedAt`. Key-auth cache must be invalidated (short TTL + explicit invalidation). |
| **Validate** | Hash lookup by `keyHash` (constant-time compare via existing `hashToken` equality on indexed hash — lookup itself is the comparison). Checks: status active, not expired, user not deleted/suspended/banned. Result cached ≤30–60s in-process, invalidated on revoke/rotate. |
| **Expire** | `expiresAt` checked during validation; a background TTL index is insufficient because status must flip explicitly — validation short-circuits on `expiresAt < now`. |
| **Scope** | Per-key `scopes: CapabilityScope[]`; enforced at the capability gate before routing. |

## F. Request lifecycle

```text
Generated App → SDK → POST /api/runtime/v1/ai/text  (Authorization: Bearer atai_…)
  1. Edge/proxy pass-through (runtime paths added to PUBLIC_API_PREFIXES in proxy.ts —
     they authenticate with Bearer keys, not cookies)
  2. authenticateKey(): hash → ApiKeyDoc (cached) → user lookup (deleted/suspended/banned?)
  3. resolveContext(): userId + projectId + environment from the key (NOT from body/headers)
  4. authorize(): capability ∈ key.scopes ? : authorization_error
  5. rateLimit(): fixed-window per key and per project (reuses Mongo limiter)
  6. validateRequest(): zod schema per capability/operation → invalid_request
  7. checkEntitlement(): getAvailableCredits(userId) ≥ estimate ? : insufficient_entitlement (402)
  8. route(): CapabilityRegistry[capability].resolve(operation, model, env) → ProviderAdapter
  9. adapter.execute(): provider call with server-side credentials; streaming forwarded as-is
 10. normalize(): provider response → stable Atai response shape (+ normalized errors)
 11. recordUsage(): insert runtime_usage + consumeCredits({ transactionType: "runtime_usage",
     idempotencyKey: requestId }) — best-effort/failure-tolerant
 12. return response (+ X-Atai-Request-Id)
```

**Sync vs async:** steps 1–8 and 12 are always synchronous (cheap, indexed).
Step 9 for text/chat is synchronous streaming (SSE pass-through). Step 11 usage
recording is **asynchronous** (`after()`/fire-and-forget with retry) — it must never
add latency or fail the request. Long-running generations (video, large image batches)
should become async jobs (Phase 8+; provider verification required first).

## G. SDK architecture

`packages/atai-sdk` — a **separate workspace package, part of the same ATAI workspace**,
communicating only with the Runtime API over HTTP. Zero runtime dependencies
(fetch-based), TypeScript-first, ESM+CJS.

```text
packages/atai-sdk/src/
├── client.ts          # AtaiClient: fetch wrapper, retries (429/5xx, exponential backoff,
│                      #   honors Retry-After), timeouts, request-id propagation
├── auth.ts            # Bearer header injection; env-var fallback ATAI_API_KEY
├── capabilities/      # ai, search, email, payments… — one module per capability
├── errors.ts          # mirror of server error categories, typed AtaiError subclasses
├── streaming.ts       # SSE parsing for text streaming
└── types.ts           # request/response contracts (shared source or generated)
```

- Public surface (conceptual): `new Atai({ apiKey })` → `atai.ai.text({ model, messages, stream? })`,
  `atai.search.web({ query })` — final names decided per verified provider capabilities.
- The SDK contains **no provider secrets and no provider SDKs** — it only talks to
  `ATAI_BASE_URL` (default the runtime API host, overridable for self-host/tests).
- Contract sharing: the request/response TypeScript types should live in one place
  (e.g. `lib/runtime/contracts/` imported by the SDK package via workspace path, or
  published types) so the API and SDK cannot drift.
- Versioning: SDK pins a major; server keeps `/api/runtime/v1/*` backward-compatible;
  the response includes an API version field for future negotiation.

## H. Provider adapter architecture

```typescript
// lib/runtime/providers/types.ts (future — not implemented in Phase 1)
interface ProviderAdapter<Req, Res> {
  id: string                                  // "openrouter"
  capability: CapabilityId                    // "ai.text"
  supportedOperations: OperationId[]
  models: ModelDescriptor[]                   // verified list only
  estimateCost(req: Req): CreditEstimate      // for entitlement pre-check
  execute(req: Req, ctx: RuntimeContext): Promise<Res | StreamedRes>
  mapError(err: unknown): AtaiRuntimeError    // → normalized category
}
```

```typescript
// CapabilityRegistry (data, not code — loaded from a verified manifest)
REGISTRY["ai.text"] = { adapters: [OpenRouterAdapter], defaultProvider: "openrouter" }
REGISTRY["search.web"] = { adapters: [FirecrawlAdapter], defaultProvider: "firecrawl" }
```

Resolution order: requested model → capability registry → provider adapter →
estimate → execute. The registry is **never written speculatively**: an adapter is
added only after its provider documentation has been verified (rule in §30 of the
brief). Providers are an implementation detail — no provider names in SDK types,
responses, or error messages.

## J. Security model

- **Key security:** SHA-256-hashed keys only (no plaintext at rest), shown once,
  prefix-only display, constant-time-safe lookup, optional expiry, rotation with grace,
  immediate revocation with cache invalidation.
- **Provider secret security:** all provider credentials stay server-side, read via
  `lib/env.ts`-style per-feature getters. They are never returned by any runtime
  response, never logged (logger redaction already strips `*api*key*`/`token`/`secret`),
  and never shipped in the SDK.
- **Browser security:** the server key is never embedded in browser JS. Browser clients
  of generated apps must route through the generated app's own backend. A later phase
  may add a separate **publishable restricted key** (origin/allowlist-bound, narrow
  scopes, hard rate limits) — architectural placeholder only; not finalized until the
  real browser-facing use cases are inspected (per §16 of the brief).
- **Account isolation:** every runtime request's identity comes from the key record —
  never from client-supplied user/project identifiers. Cross-tenant access is
  structurally impossible because the capability handlers only ever touch resources
  derived from the authenticated key.
- **Project/environment isolation:** key is bound to one project + environment;
  handlers enforce project scope on every operation (e.g. `atai.db` operations may only
  address the key's own Totalum project).
- **Rate limiting:** three layers reusing the existing Mongo fixed-window limiter —
  per key, per project, per capability — plus request-size limits and provider timeout
  policies (the codebase already has timeout discipline in its integration clients).
- **Audit logging:** `runtime_usage` per request (no secrets, no bodies, hashed IP if
  needed); the structured logger's redaction reused everywhere.
- **Internal-key lesson:** the new system must not repeat the `ATAI_INTERNAL_KEY`
  pattern (static shared secret, non-constant-time compare, key material logged).

## K. Billing/usage architecture

- **Attribution:** every runtime request resolves to `userId` from the key; consumption
  is charged to that user via the existing unified credit service — the single
  authoritative ledger (`lib/billing/credit-service.ts`). No parallel balance system.
- **Flow:** estimate (adapter) → entitlement check (`getAvailableCredits`) → execute →
  measure (provider-reported usage where available) → `consumeCredits` with
  `transactionType: "runtime_usage"` and `idempotencyKey: requestId` (ledger's unique
  index already guarantees no double-charge on retries).
- **No prices invented in this phase.** Per-unit pricing, markup, and model-tier
  multipliers belong in a future phase, admin-configurable via the existing
  `app_settings` runtime-config pattern (a new `runtime` section, same layering/fallback
  semantics as `getBuildTierCosts()`).
- **Existing payment rails unchanged:** Dodo subscriptions/top-ups keep working as-is;
  runtime consumption simply draws down the same subscription/permanent credit buckets.

## L. Generated application integration (future)

Today, when a build finishes, `buildSummary.secretKeysNeeded` surfaces missing secret
keys and the owner pastes values into Totalum secrets (`POST /api/projects/:id/secrets`).
The eventual integration:

1. At build time (a later phase, untouched for now), the pipeline marks capabilities
   with `provider_mode: atai` in the specification (spec schema is a zod object —
   additive optional fields like `runtimeRequirements` would fit without breaking
   old specs).
2. At deploy/success time, Atai provisions the app: create `api_keys` doc for the
   project (if none), then call the **existing** Totalum secrets endpoint to inject
   `ATAI_API_KEY` + `ATAI_PROJECT_ID` + `ATAI_ENVIRONMENT` into the generated app's
   environment — exactly the mechanism that already exists in
   `app/api/projects/[id]/secrets/route.ts`. No Totalum changes required.
3. The generated app's code (template instructions) imports the SDK and uses capabilities.

This keeps the build pipeline untouched: only the deploy-time post-processing adds keys.

## M. Deployment architecture

- **Runtime API:** starts inside the existing Next.js app under `/api/runtime/v1/*` —
  deployed together with Atai, zero infra changes — but the code is structured as an
  isolated service (`lib/runtime/*`) so it can lift out into `apps/runtime-api` as a
  separate workspace app/deployment when justified. Nothing depends on same-process
  co-location (stateless route handlers + Mongo).
- **SDK:** independent `packages/atai-sdk` workspace package from Phase 7, separate
  semver lifecycle, publishable to npm when ready. It is part of the same workspace but
  versioned, built, and released independently of the Atai application.

## Risks, unresolved questions, and assumptions requiring approval

### Risks
1. **Per-request credit charging has no precedent in the codebase** — all charging today
   is route-scoped build-time. Latency of the Mongo-transaction ledger on a hot path
   needs a measurement in Phase 5 (mitigation: async usage recording + optimistic
   balance check, with reconciliation).
2. **Flat identity model** — no orgs/teams. Multi-tenancy is user → project → key, which
